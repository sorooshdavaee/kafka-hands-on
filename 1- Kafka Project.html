پروژه: Kafka Hands-on برای Distributed Order Processing System

هدف پروژه

شبیه‌سازی یک سیستم واقعی سفارش (Order Processing) که تمام مفاهیم ضعف‌دار (ISR, Partition Assignment, Exactly-once, Schema Evolution, Consumer Lag) رو عملاً لمس کنی.

معماری کلی پروژه

[Order API (C#)] --> [Kafka: orders-topic] --> [Consumer Group: Payment Service]
–> [Consumer Group: Notification Service]
–> [Consumer Group: Inventory Service]

سه تا Consumer Group مستقل که به یک Topic گوش می‌دن (شبیه‌سازی Choreography Saga).

Step 1: راه‌اندازی Kafka Cluster با Docker (روز ۱-۲)

چیزی که باید بسازی:

  • Docker Compose با ۳ Broker Kafka (نه ۱ broker — این مهمه چون ISR رو فقط با چند Broker می‌بینی)
  • ۱ Zookeeper یا KRaft mode (پیشنهاد: KRaft چون جدیدتره و Zookeeper رو حذف کرده)
  • ۱ Kafka UI (مثل provectuslabs/kafka-ui) برای مشاهده Partition/Replica/ISR به صورت بصری

تسک عملی:

  • یک Topic به اسم orders با --partitions 6 --replication-factor 3 بساز
  • با دستور kafka-topics.sh --describe خروجی رو ببین و دقیقاً بفهم Leader/Replicas/ISR یعنی چی

چک‌پوینت یادگیری:
باید بتونی توضیح بدی چرا Partition Count بعد از ساخت Topic راحت افزایش پیدا می‌کنه ولی کاهش نه، و replication-factor چطور روی Broker های موجود توزیع می‌شه.

Step 2: Producer با C# (روز ۳-۴)

چیزی که باید بسازی:
یک ASP.NET Core Web API ساده (POST /orders) که با Confluent.Kafka پیام Order رو Produce کنه.

نکات فنی که باید پیاده کنی، نه فقط بخونی:

  • acks=all رو تنظیم کن و تفاوتش رو با acks=1 در سناریوی Broker Down تست کن
  • Idempotent Producer (enable.idempotence=true) رو فعال کن
  • یک Partition Key معنادار انتخاب کن (مثلاً CustomerId) و بفهم چرا این کار Order Guarantee در سطح مشتری می‌ده نه در سطح کل Topic

تسک عملی (خیلی مهم):
موقع تست، یکی از ۳ Broker رو با docker stop خاموش کن درحالی که Producer داره پیام می‌فرسته. رفتار Cluster (Leader Election جدید، ISR Shrink) رو در Kafka UI مشاهده کن.

Step 3: Consumer با C# — سه سرویس مستقل (روز ۵-۷)

چیزی که باید بسازی:
سه Console App جدا (نه یک پروژه):

  1. PaymentService — Consumer Group: payment-group
  2. NotificationService — Consumer Group: notification-group
  3. InventoryService — Consumer Group: inventory-group

نکات فنی که باید پیاده کنی:

  • Manual Commit به جای Auto Commit (enable.auto.commit=false) — و بفهمی چرا در سیستم واقعی این حیاتیه
  • تفاوت Commit() بعد از پردازش (At-least-once) در برابر قبل از پردازش (At-most-once) رو با کد تست کن، نه فقط تئوری

تسک عملی برای Partition Rebalancing:

  • یک نمونه از PaymentService رو اجرا کن، ببین همه ۶ Partition بهش اختصاص پیدا می‌کنه
  • یک نمونه دیگه از همون سرویس (همون Consumer Group) اجرا کن، ببین Rebalance اتفاق می‌افته و Partition ها بین دو Instance تقسیم می‌شه
  • این کار رو با Strategy های مختلف (RangeAssignor vs CooperativeStickyAssignor) امتحان کن و تفاوت رفتار Rebalance (Stop-the-world در برابر Incremental) رو مشاهده کن

Step 4: Consumer Lag Monitoring (روز ۸)

چیزی که باید بسازی:

  • یک Consumer که عمداً کند پردازش می‌کنه (مثلاً Thread.Sleep(500))
  • با دستور kafka-consumer-groups.sh --describe --group payment-group مقدار Lag رو ببین

چک‌پوینت:
باید بفهمی Lag یعنی چی (تفاوت High Watermark و Committed Offset) و چطور می‌شه Alert روش گذاشت.

Step 5: Exactly-once با Transactional API (روز ۹-۱۰)

سناریوی واقعی که باید پیاده کنی:
PaymentService بعد از خوندن پیام Order، باید یک پیام جدید به Topic دیگه (payment-results) بفرسته — این Read-Process-Write باید Atomic باشه.

پیاده‌سازی:

  • از Producer با TransactionalId استفاده کن
  • BeginTransaction(), SendOffsetsToTransaction(), CommitTransaction() رو پیاده کن
  • عمداً یک Exception بنداز وسط پردازش و ببین با AbortTransaction() هم پیام جدید ارسال نمی‌شه و هم Offset اصلی Commit نمی‌شه

این دقیقاً همون چیزیه که در Outbox Pattern با DB اتفاق می‌افته، ولی این بار در سطح Kafka به Kafka.

Step 6: Schema Evolution با Avro (روز ۱۱-۱۲)

چیزی که باید بسازی:

  • یک Schema Registry (Confluent Schema Registry) به Docker Compose اضافه کن
  • Order Message رو با Avro Schema تعریف کن (نه JSON ساده)

تسک عملی برای فهم Backward/Forward Compatibility:

  • یک Field جدید (مثلاً Discount) با Default Value به Schema اضافه کن — Consumer قدیمی رو بدون تغییر اجرا کن، ببین کرش نمی‌کنه (Backward Compatible)
  • یک Field رو Rename کن بدون Alias — ببین Schema Registry رد می‌کنه (Compatibility Break)

Step 7: Log Compaction (روز ۱۳-۱۴)

چیزی که باید بسازی:
یک Topic جدید با cleanup.policy=compact بساز (مثلاً customer-latest-status) که فقط آخرین وضعیت هر مشتری رو نگه داره (Key = CustomerId).

تسک:
چند پیام با Key یکسان بفرست، kafka-console-consumer رو بعد از Compaction اجرا کن و ببین فقط آخرین Value مونده.

سوالاتی که باید بعد از این پروژه بتونی جواب بدی

دسته ۱: Broker/Cluster

  1. اگه Replication Factor سه باشه و ISR به یک برسه، چه اتفاقی برای acks=all می‌افته؟
  2. تفاوت Unclean Leader Election فعال و غیرفعال در سناریوی از دست رفتن داده چیه؟

دسته ۲: Producer

  1. چرا فعال کردن enable.idempotence=true به تنهایی Duplicate در سطح Consumer رو حل نمی‌کنه؟
  2. اگه Partition Key رو بر اساس CustomerId انتخاب کنی ولی تعداد Customer خیلی بیشتر از Partition باشه، چه مشکلی (Hot Partition) ممکنه پیش بیاد و راه‌حلش چیه؟

دسته ۳: Consumer/Rebalancing

  1. تفاوت رفتار RangeAssignor و CooperativeStickyAssignor هنگام اضافه شدن یک Consumer جدید چیه؟ (باید بتونی بگی چرا یکی Stop-the-world هست)
  2. اگه Consumer بعد از پردازش پیام کرش کنه ولی قبل از Commit، در حالت At-least-once چه اتفاقی می‌افته؟ Idempotency در سمت Consumer چطور این مشکل رو حل می‌کنه؟

دسته ۴: Exactly-once

  1. Transactional Producer چطور تضمین می‌ده که هم Offset Commit و هم پیام جدید با هم Atomic باشن؟ (باید بتونی نقش __transaction_state Topic رو توضیح بدی)
  2. تفاوت Exactly-once Semantics در سطح Kafka-to-Kafka با Exactly-once در سناریوی Kafka-to-Database (که همون Outbox Pattern لازمه) چیه؟

دسته ۵: Schema Evolution

  1. چرا اضافه کردن Field بدون Default Value، Backward Compatibility رو می‌شکنه؟
  2. اگه بخوای یک Field رو Rename کنی بدون شکستن Compatibility، چیکار باید بکنی؟

دسته ۶: Monitoring

  1. Consumer Lag بالا لزوماً به معنی مشکل نیست — در چه شرایطی Lag بالا طبیعیه؟
  2. تفاوت Lag و Consumer Group Rebalance Rate بالا از نظر تشخیص مشکل عملیاتی چیه؟
