ORM و Database

بخش انتخاب دلیل
ORM EF Core ساده و آشنا، UoW طبیعتاً با SaveChanges پیاده میشه
DB PostgreSQL Debezium نیاز به wal_level = logical داره؛ MySQL هم پشتیبانی میشه ولی Postgres تمیزتره

نکته مهم: OutboxMessage رو باید توی همون DbContext و همون Entity که Order رو داره تعریف کنی، تا SaveChanges یکجا هر دو رو توی یک تراکنش commit کنه. این خودِ اصل Outbox Pattern هست.

public class Order : AggregateRoot
{
    // ...
    public void Place()
    {
        // domain logic
        AddDomainEvent(new OrderPlacedEvent(...));
    }
}

توی EF Core interceptor یا SaveChangesAsync override، Domain Event ها رو serialize کن و به‌عنوان ردیف در جدول outbox_messages اضافه کن — همون تراکنش، همون commit.

یک نکته فنی مهم درباره‌ی Kafka Streams

Kafka Streams یک کتابخونه‌ی JVM-only هست — معادل رسمی .NET نداره. دو راه داری:

  1. با Confluent.Kafka client دستی یک Stream Processor بسازی (Consume از topic → state رو نگه‌دار → Produce به compacted topic) — خودت state store رو شبیه‌سازی می‌کنی.
  2. برای Debezium Outbox Router از یک SMT (Single Message Transform) به اسم Outbox Event Router استفاده کنی که خودِ Debezium داره — این بهت اجازه میده مستقیم از جدول outbox، event های تمیز و ساختاریافته به topic بفرستی، بدون نیاز به پردازش اضافه.

پیشنهاد من: برای ReadModel.Processor گزینه ۱ رو با Confluent.Kafka بزن، چون هم واقعی‌تره برای مصاحبه‌های خارج، هم می‌فهمی زیر پوست Kafka Streams چه اتفاقی می‌افته (که مهم‌تر از استفاده از کتابخونه‌ست).

ایده‌ی جذاب‌سازی: Traffic Generator Worker

دقیقاً حرفت درسته — سیستمی که ساکنه، انگیزه نمیده. پیشنهاد:

public class TrafficGeneratorWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        var faker = new Faker<CreateOrderRequest>()
            .RuleFor(o => o.CustomerName, f => f.Name.FullName())
            .RuleFor(o => o.Amount, f => f.Random.Decimal(10, 5000));

        while (!ct.IsCancellationRequested)
        {
            var order = faker.Generate();
            await _httpClient.PostAsJsonAsync("/orders", order, ct);

            // فاصله‌ی تصادفی برای شبیه‌سازی ترافیک واقعی (نه یکنواخت)
            var delay = Random.Shared.Next(500, 3000);
            await Task.Delay(delay, ct);
        }
    }
}

از پکیج Bogus (معادل Faker.js توی .NET) استفاده کن.

برای هیجان بیشتر - Chaos Injection

یک endpoint یا سوییچ بذار که وسط اجرای Worker:

  • سرویس Order.Api رو با docker kill قطع کنه وسط یه batch از request ها
  • بعد ببینی چند تا outbox message pending موند، Debezium بعد از up شدن دوباره چطور ادامه میده
  • توی Kafka UI (مثل provectuslabs/kafka-ui) لایو ببینی topic ها پر میشن

این دقیقاً سناریوی سوال ۴ و ۵ قبلی رو برات قابل مشاهده می‌کنه به جای صرفاً تئوری.

سوال برگردون بهت: برای ReadModel.Processor، ترجیح میدی state رو در حافظه (in-memory ConcurrentDictionary) نگه داری یا از یه storage سبک مثل RocksDB/SQLite به‌عنوان local state store استفاده کنی (که خودِ Kafka Streams واقعی هم همینو انجام میده)؟

فایل‌های کلیدی که باید دقیق طراحی بشن

۱. OutboxSaveChangesInterceptor.cs

public class OutboxSaveChangesInterceptor : SaveChangesInterceptor
{
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData, InterceptionResult<int> result)
    {
        var context = eventData.Context;
        var domainEvents = context.ChangeTracker
            .Entries<AggregateRoot>()
            .SelectMany(e => e.Entity.DomainEvents);

        foreach (var domainEvent in domainEvents)
        {
            context.Set<OutboxMessage>().Add(
                OutboxMessage.FromDomainEvent(domainEvent));
        }

        return base.SavingChanges(eventData, result);
    }
}

این interceptor توی AppDbContext رجیستر میشه و باعث میشه Domain Event ها همون تراکنش SaveChanges به outbox اضافه بشن — بدون نیاز به تغییر توی Handler.
