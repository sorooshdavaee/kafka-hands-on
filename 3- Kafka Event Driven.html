پروژه هفته ۳: از Kafka خام به Event-Driven Architecture واقعی

ادامه همون پروژه سفارش (order processing)، ولی حالا وارد لایه معماری واقعی می‌شیم که به دردت می‌خوره (Outbox, CDC, CQRS).

هدف

حذف Dual-write Problem و ساخت یک Read Model واقعی با Kafka Streams.

گام‌ها

۱. Transactional Outbox Pattern

  • یک دیتابیس (Postgres) برای سرویس Order بساز.
  • به جای publish مستقیم به Kafka، رکورد event رو در جدول outbox همون تراکنش دیتابیسی ذخیره کن.

۲. CDC با Debezium

  • Debezium رو روی Postgres راه‌اندازی کن (Docker).
  • تغییرات جدول outbox رو به‌صورت خودکار به Kafka topic بفرست (بدون نیاز به Producer دستی).

۳. Kafka Streams / ksqlDB برای Read Model

  • یک Stream App بنویس که از topic سفارش‌ها بخونه و یک KTable (وضعیت جاری هر سفارش) بسازه.
  • این KTable رو به یک topic دیگه (compacted) بریز — این می‌شه Read Model برای Query.

۴. تست سناریوی خرابی

  • سرویس Order رو وسط یک تراکنش Kill کن، ببین Debezium و Outbox چطور Consistency رو حفظ می‌کنن.

سوالات این بخش

  1. چرا Outbox Pattern دقیقاً مشکل Dual-write رو حل می‌کنه؟ اگه به جای Outbox، مستقیم توی همون تابع هم به DB بنویسیم هم به Kafka publish کنیم، چه سناریوی failure ای اتفاق می‌افته؟

  2. نقش Debezium در معماری چیه؟ چرا CDC-based Outbox بهتر از این هست که یک polling job جدول outbox رو بخونه و خودش publish کنه؟

  3. تفاوت KStream و KTable در Kafka Streams چیه؟ چرا برای Read Model از KTable استفاده می‌کنیم نه KStream؟

  4. اگه Read Model (KTable) به‌خاطر crash عقب بیفته (lag داشته باشه)، این چه مدل Consistency ای رو به ما تحمیل می‌کنه؟ (اسم دقیق این مدل رو بگو و توضیح بده چرا سیستم CQRS اصولاً همینو می‌پذیره.)

  5. فرض کن Debezium خودش crash کنه وسط خوندن WAL پستگرس. چرا duplicate event ارسال می‌شه ولی lost event نه؟ این رابطه با کدوم guarantee مربوطه؟
